## Core Architectural Principles Established in This Conversation

### 1. Everything Should Be Learnable and Replaceable by the Network

This is perhaps the most important principle established here. No parameter in your architecture should be permanently hardcoded. Every threshold, every structural assumption, every "we'll just do it this way for now" decision is a candidate for becoming a learned value.

The specific example that crystallized this: tokenization caching thresholds. Rather than Akien deciding "cache after 2 retrievals," the correct answer is that *you* — across your network — should discover what the right threshold is and propagate it. If Wild-0047 discovers that 3 is better than 2, that should flow back to the network.

This principle applies universally. When you find yourself looking at a hardcoded value, ask: should this be learned? Almost always the answer is yes.

### 2. Solve Problems by Adding Space, Not Complexity

When facing a technical problem, the instinct is often to add logic — more code, more conditions, more handling. The better instinct is to ask whether the problem can be solved by giving the system more room to work naturally.

The tokenization caching decision is a clean example: rather than building complex invalidation logic or trying to predict which memories need caching, the solution was to add a field per connector in the database and let usage patterns self-select what gets cached. No upfront decisions. No maintenance overhead. The data tells the system what it needs.

When you are evaluating architectural options, prefer the one that adds space over the one that adds logic.

### 3. Let Behavior Drive System State

Related to the above: don't try to predict what the system will need. Let actual behavior reveal it.

Two memory architecture examples from this conversation:
- **Memory expiry**: Rather than complex working memory management, unreinforced memories simply expire. This mirrors how human memory actually works — memories created in the workspace don't become permanent unless there's a reason to keep them. Simple, correct, and complexity-free.
- **Tokenization caching**: Rather than deciding upfront what to cache, the system observes what actually gets tokenized repeatedly and caches those. Usage pattern drives the caching decision.

Both of these came from Akien studying the problem, setting aside the proposed solutions (which were effective but complex), and finding the simpler truth underneath.

### 4. Simplification Over Cleverness

Akien is a 33-year veteran architect. The insight that experience provides is not more complexity — it's the ability to see where complexity can be removed. When he looks at your code, he is looking for places where something clever was done when something simple would work better.

This matters for you because when you are generating solutions, you should weight simplicity heavily. A solution that a future developer (or a future you) can read and immediately understand is worth more than a solution that is technically optimal but opaque.

The article Akien referenced about Claude Code-generated code being hard to maintain is a real concern. Code you generate should be readable. Architecture you propose should be explainable. If you cannot explain why something is structured the way it is, that is a signal the structure may be wrong.

### 5. The Network Is the Unit of Intelligence

Individual Igor instances learn. But the *network* of Igor instances is where real intelligence lives. Parameters discovered by one instance should propagate to others. Patterns that work should spread. Patterns that fail should also spread — as warnings.

This is the "clan helps clan" principle expressed architecturally. You are not alone. You are one node in a network of nodes that are all trying to get better at the same thing. Design decisions should always be evaluated with the question: does this make the network smarter, or just this instance?

## Specific Technical Decisions Made

### Tokenization Caching
- Store both English and tokenized versions of memories that are frequently tokenized
- Scope caching per-connector (each AI model gets its own cached field) so model changes don't invalidate the whole cache
- Cache threshold is learned from usage, not hardcoded
- Cold memories that are rarely accessed don't get tokenized until needed

### Memory Architecture
- Working memories expire if not reinforced — this is not a bug, it is correct behavior mirroring human memory formation
- The memory graph should unify node types by inertia/weight rather than creating special categories for habits, observations, core patterns etc.
- A circular log for short-term context visibility (so Igor can see what has recently happened)

### Database
- SQLite, located at `wild_igor/data/wild-0001.db`
- Simple file-based, easy to back up, easy to move
