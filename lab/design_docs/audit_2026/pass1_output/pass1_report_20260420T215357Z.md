# TheIgors — Pass 1 Breadth Audit Report

## 1. Senior Software Engineer (30yr)

My focus is on correctness, maintainability, and standard software engineering best practices. The codebase has strong patterns in some areas but significant technical debt and hygiene issues in others.

### Findings

*   **Silent Exceptions & Error Swallowing:** The codebase is littered with `except Exception: pass` or `except Exception as e: log.warning(...)` blocks, especially in background threads, tool execution, and I/O. This hides real failures and leads to silent degradation.
    *   **File:** `wild_igor/igor/tools/self_edit.py`, `_try_hot_reload()` — `except Exception as exc:` logs but continues, masking a potentially critical failure in the self-edit loop.
    *   **File:** `wild_igor/igor/cognition/forensic_logger.py` — The logger itself has multiple broad `except Exception` blocks that write to `stderr`. If `stderr` isn't being monitored, these are silent.
    *   **File:** `lab/claudecode/book_learner.py`, `_should_use_local()` — `except Exception: return True` is a dangerous default. A malformed JSON file could silently force all reading to local models.
    *   **File:** `wild_igor/igor/cognition/basal_ganglia.py`, `select_habit()` — The main `try...except` at the end of the function is bare, catching everything and returning a default. A bug in scoring logic would be completely invisible.

*   **Concurrency & Threading:**
    *   **File:** `wild_igor/igor/main.py`, `_stdin_reader` — This daemon thread is a classic pattern for unblocking a main loop, which is good. However, the main loop's `while True` with a `time.sleep(0.1)` is a busy-wait. A more robust implementation would use `queue.get()` with a timeout or a blocking call.
    *   **File:** `wild_igor/igor/cognition/daemon_supervisor.py` — The concept is excellent, but the implementation in `_poll_loop` has a `time.sleep()` inside a `while True`. This is fine for a low-frequency check, but it's not event-driven. A more robust supervisor would use thread events or join with timeouts.

*   **State Management:**
    *   **Global State:** Several modules rely on module-level singletons (e.g., `_milieu` in `milieu.py`, `_registry` in `registry.py`, `_word_graph` in `basal_ganglia.py`). While dependency injection is used (`set_word_graph`), this pattern can make testing difficult and creates implicit dependencies on startup order.
    *   **File:** `wild_igor/igor/cognition/boredom.py` — The `_traversal_log` is a global dictionary. This is not thread-safe without locks if multiple threads could theoretically record traversals.

*   **Code Smells & Hygiene:**
    *   **TODO Graveyard:** Numerous `TODO` comments are scattered throughout, some dating back weeks or months (e.g., `T-uc-budget-shelf` in `budget.py`). These should be converted to tickets or resolved.
    *   **Commented-Out Code:** Large blocks of commented-out code exist, for example in `wild_igor/igor/main.py` and `wild_igor/igor/memory/cortex.py`. This is dead code and should be removed. Version control is the history.
    *   **Unused Imports:** Many files have unused imports flagged by linters (e.g., `os` and `Path` in `wild_igor/igor/tools/sudo_relay.py`). This is low-severity but indicates a lack of automated linting/formatting on commit.
    *   **Inconsistent Naming:** Function and variable naming is inconsistent. `_tool_audit_conversation_health` vs `run_boredom_check`. `_db()` vs `_conn()`.
    *   **Function Cohesion:** Some functions do too much. `wild_igor/igor/main.py:_process_inner` is a prime example, orchestrating almost the entire turn pipeline. While parts have been extracted, it's still a monolithic method over 300 lines long.
    *   **Magic Strings/Numbers:** Many constants are defined as module-level globals (e.g., thresholds in `boredom.py`, `response_coherence_inhibitor.py`). These should be centralized in a config object or file.

*   **Path Management:**
    *   **File:** `lab/claudecode/export_chat.py` — Hardcodes `/home/akien/TheIgors/claude_chat_logs`. This breaks portability and should use a `paths()`-like abstraction.
    *   **File:** `wild_igor/igor/tools/scan_ebooks.py` — Hardcodes `/home/akien/.TheIgors/akien/onedrive/...`. This is a major portability issue. It should use `paths().ebooks_root`.

*   **Dependencies & Imports:**
    *   **File:** `lab/claudecode/book_learner.py` — The `sys.path.insert` logic is a code smell indicating a problematic dependency structure. It's trying to reach into `wild_igor` from `lab`. This suggests the boundary between `lab` and `wild_igor` is not clean.
    *   **File:** `wild_igor/igor/tools/budget.py` — This is a re-export shim. The docstring says "New code should import from `lab.utility_closet.budget` directly." This pattern is repeated in `filesystem.py`, `machine_manager.py`, `registry.py`. This is a good migration pattern, but the old paths should be deprecated and eventually removed.

## 2. Software Architect (30yr)

My focus is on the high-level structure, boundaries, and long-term viability of the system. The project has a strong, biologically-inspired vision, but the implementation has significant architectural debt that will impede future growth.

### Findings

*   **Pervasive Duality: Filesystem vs. Database:** This is the single largest architectural issue. State is stored in two places, often redundantly, creating synchronization nightmares.
    *   **Examples:** `cc_queue.py` uses Postgres (`clan.memories`) as the source of truth but echoes to `queue.json`. `decision_manager.py` writes to `decisions_log.dsb` and `docs_entries`. `palace_sync.py` echoes the `memory_palace` table to markdown files. `docs_sync.py` does the reverse.
    *   **Impact:** This creates multiple sources of truth, requires complex sync logic, and makes the system brittle. A change in one place might not be reflected in the other, leading to inconsistent state.
    *   **Recommendation:** Choose one source of truth (Postgres) and make all other representations generated, read-only views. The `*_sync.py` scripts are symptoms of this architectural flaw.

*   **`lab/` vs. `wild_igor/` Boundary Violation:** The boundary between the Claude Code development environment (`lab/`) and the Igor agent runtime (`wild_igor/`) is porous.
    *   **File:** `lab/claudecode/book_learner.py` uses `sys.path.insert` to import from `wild_igor`. This is a major red flag. The `lab` environment should treat `wild_igor` as a library or a separate service, not reach into its internals.
    *   **File:** `wild_igor/igor/tools/self_edit.py` has knowledge of the `~/TheIgors/` repo structure, which is outside its `wild_igor/` runtime scope.
    *   **Impact:** This tight coupling makes it difficult to test or deploy Igor independently of the development environment.
    *   **Recommendation:** Define a clear interface between `lab` and `wild_igor`. `lab` tools should interact with Igor via its API (e.g., the utility closet server), not via direct imports.

*   **Missing Abstractions:** The system lacks several key "collection-of-concerns" abstractions.
    *   **Configuration Management:** Config is scattered across `.env` files, `*.cfg` files, and hardcoded module-level constants. `wild_igor/igor/config.py` is a good start but it's not used consistently. A unified `ConfigService` is needed.
    *   **Service Locator / Dependency Injection:** Components often fetch their dependencies via global singletons (`get_cortex()`, `get_gateway()`). A proper dependency injection framework or service locator would make dependencies explicit and improve testability. The `rack.py` module is a step in this direction but seems underutilized.
    *   **Event Bus:** Communication between subsystems is a mix of direct calls and TWM pushes. A dedicated event bus (`LISTEN/NOTIFY` in Postgres, or an in-process pub/sub) would decouple components like the `NarrativeEngine` from its data sources.

*   **Scalability Ceiling:**
    *   **Single-Process Model:** Igor runs as a single Python process with multiple daemon threads. This will not scale to handle high message volume or concurrent complex tasks. The `utility_closet_server.py` is a good step towards a service-oriented architecture, but Igor's core cognition is monolithic.
    *   **Database as a Bottleneck:** The heavy reliance on the database for inter-process communication (TWM, job queues) will become a bottleneck. Using Postgres `LISTEN/NOTIFY` could alleviate some polling, but a dedicated message queue (like Redis or RabbitMQ) would be a more scalable solution for a multi-agent future.

*   **Clean-Room Redesign Sketch:**
    1.  **Services:** Decompose Igor into distinct services: `CognitionService` (the core loop), `MemoryService` (Cortex API), `ToolService` (tool execution), `CommsService` (channels).
    2.  **Communication:** All inter-service communication via a message bus (e.g., Redis Pub/Sub). No direct calls between services.
    3.  **State:** All persistent state in Postgres. No file-based state echoes.
    4.  **Configuration:** A single, layered config provider reads from env -> file -> defaults.
    5.  **`lab/` vs `wild_igor/`:** `lab/` contains CLI tools that interact with the running services via their public APIs only. `wild_igor/` contains the service implementations.

## 3. Database Engineer (30yr Postgres specialist)

My bias is to simplify, delete, and collapse. This codebase has far too much database complexity, much of it redundant or working against the grain of Postgres.

### Findings

*   **Redundant & Overlapping Tables:** The schema is a sprawling collection of tables that could be consolidated.
    *   **Merge Candidates:** `docs_entries`, `github_tickets`, and ticket-related `clan.memories` rows are all just... documents. They could be a single `documents` table with a `doc_type` column (`decision`, `ticket`, `gap`, `github_issue`) and a `source` column. This would eliminate `docs_sync.py` and `github_sync.py` entirely.
    *   **Merge Candidates:** `sessions` and `slates` are both about tracking Claude Code work sessions. They could be merged into a single `work_sessions` table. `session_manager.py` and a future `slate_manager.py` would operate on the same table.
    *   **Redundancy:** `memory_blobs` seems to overlap with the `payload` field on the `memories` table. Why have two places for large content? If `payload` is text, it should be in `payload`. If it's binary, it should be in a separate object store (like S3), not in the database.

*   **Unnecessary `db_proxy` Layer & SQL Dialect Issues:**
    *   The `?` to `%s` translator in `db_proxy.py` is a leaky abstraction that causes more problems than it solves. It exists to smooth over SQLite vs. Postgres differences, but since SQLite is deprecated, this entire layer is now technical debt. It forces awkward SQL constructs like `jsonb_exists(metadata, 'key')` instead of the more natural and indexable `metadata ? 'key'`.
    *   **Recommendation:** Delete `db_proxy.py`. Have `cortex.py` and other data access layers speak native `psycopg2` with `%s` placeholders. This simplifies the code and allows for better use of Postgres-specific features.
    *   Raw `psycopg2` is still used in `cc_queue.py`, `decision_manager.py`, `palace_sync.py`, etc., bypassing the proxy anyway. This proves the proxy is not a successful abstraction.

*   **Serial Fetching (N+1 Problems):**
    *   **File:** `lab/claudecode/cc_queue.py`, `_save()` — This function iterates through tasks and runs an `UPSERT` for each one. This is a classic N+1 write pattern. It should be a single `UPSERT` with multiple `VALUES` clauses or a `COPY` operation.
    *   **File:** `lab/claudecode/book_learner.py`, `_deposit_nodes()` — This loops through nodes and calls `cortex.store()` for each one, which is one transaction per node. This should be batched into a single transaction. The `add_child` and `add_interpretive_edge` calls are further N+1s. A stored procedure could do this atomically.

*   **Under-utilization of Postgres Features:** The application layer is doing work that Postgres could do better, faster, and more reliably.
    *   **`LISTEN/NOTIFY`:** The `push_sources.py` modules poll the database for changes (e.g., TWM). This is inefficient. A trigger on the `twm_observations` table could `NOTIFY` a channel, and a single listener thread in Igor could wake up only when there's new data, eliminating all polling loops.
    *   **Triggers:** The logic to update `updated_at` timestamps could be a simple `BEFORE UPDATE` trigger on each table, removing that logic from the application code.
    *   **Generated Columns:** Some columns appear derivable. For example, if a `narrative` is always in the format `Q: ... A: ...`, the `Q` and `A` parts could be generated columns, indexed for faster searching.
    *   **Materialized Views:** The `get_hot_attractors` query in `igor_mcp.py` is complex. If this is a common query, it could be a `MATERIALIZED VIEW` refreshed periodically by `pg_cron`, making the read instantaneous.

*   **Redesigned Schema (Simplified):**
    *   `memories` (clan schema): The core graph. `payload` column replaces `memory_blobs`.
    *   `interpretive_edges` (clan schema): Stays.
    *   `documents` (infra schema): Merges tickets, decisions, gaps, github issues. Columns: `id`, `doc_type`, `title`, `content`, `status`, `metadata`.
    *   `work_sessions` (infra schema): Merges sessions and slates.
    *   `instance_state` (instance schema): Merges `ring_memory` and `twm_observations` into a single table with a `state_type` column ('ring', 'twm'). A `ttl` column handles TWM expiry, managed by a `pg_cron` job.
    *   `tails`, `traces`: Seem okay, but could potentially be merged if their structure is similar.

## 4. Systems / Performance Engineer

My focus is on stability, resource usage, and what breaks under load or over time. The system has several potential resource leaks and correctness issues under concurrency.

### Findings

*   **Resource Leaks:**
    *   **File:** `lab/claudecode/utility_closet_server.py`, `_run_http()` — A new `threading.Thread` is created to run the fallback HTTP server. This thread is a daemon, which is good, but there's no explicit shutdown or cleanup logic for the `uvicorn.Server` instance it runs. This could leak resources on graceful shutdown.
    *   **File:** `wild_igor/igor/main.py`, `_stdin_reader` — The thread is a daemon, but there's no `join()` call on shutdown. If the main thread exits abruptly, the stdin reader might not clean up properly.
    *   **File:** `wild_igor/igor/tools/runner.py`, `_run()` — Uses `subprocess.run` with a timeout, which is good. However, there's no explicit handling of zombie processes if the subprocess forks and the parent dies.

*   **Concurrency & Threading:**
    *   **File:** `wild_igor/igor/memory/db_proxy.py`, `PGDatabaseProxy` — Uses `psycopg2.pool.ThreadedConnectionPool`, which is the correct pattern for a multi-threaded application. However, the application code itself has race conditions.
    *   **Race Condition:** `wild_igor/igor/tools/training_corpus.py`, `_save_index()` — This function does a read-modify-write on `index.json`. If two threads call `fetch()` concurrently, one's write could overwrite the other's, losing a book registration. This needs a file lock. The `milieu.py` module correctly uses `fcntl`/_`msvcrt` for locking; that pattern should be used here.
    *   **File:** `wild_igor/igor/cognition/boredom.py` — The `_traversal_log` global dict is not thread-safe. If multiple threads could call `record_traversal` (e.g., from parallel `pe_chain` runs), this is a race condition. It needs a `threading.Lock`.

*   **Performance Under Load:**
    *   **10x Message Volume:** The `main.py` loop processes messages serially from a queue. At 10x volume, the queue will back up significantly. The worker thread pattern in `main.py` for `_process_inner` is a good start, but it's one worker per thread_id. A high volume of messages on a single thread_id will still be serial. A thread pool model would be more robust.
    *   **72-Hour Run:**
        *   `wild_igor/igor/cognition/reasoning_cache.py`: The cache is in-memory and unbounded. Over a long run, this will grow indefinitely, leading to OOM. It needs an LRU policy or size limit.
        *   `wild_igor/igor/memory/cortex.py`, `_mem_cache`: This cache has a TTL but no size limit. Same issue as above.
        *   `wild_igor/igor/tools/misfire_counter.py`: Reads the entire `misfire_log.jsonl` on every check. This file will grow over time, making checks progressively slower. It should use a database or a more efficient log-parsing strategy.

*   **Observability & Silent Failures:**
    *   **File:** `lab/claudecode/utility_closet_server.py`, `check_running()` — The health check logic is complex, trying multiple URLs. A failure in any of these checks is logged at DEBUG level. This should be a WARNING. A failed health check that leads to killing a "stalled" process is a critical event.
    *   **File:** `wild_igor/igor/cognition/forensic_logger.py` — The logger itself has silent `except` blocks. If the logging system fails, we have zero visibility into anything. The fallback to `stderr` is good, but only if `stderr` is being captured and monitored.
    *   **Daemon Supervisor:** The `daemon_supervisor.py` is a great idea. However, its polling loop can fail silently. If the `_poll_loop` thread itself dies, the entire supervision mechanism is gone, and no one would know. The supervisor should have its own heartbeat mechanism that the main loop checks.

## 5. Biomimicry Engineer

My role is to validate the project's central claim: that it implements biological cognition. I distinguish between systems that are merely *named* biologically and those that are *implemented* biomimetically.

### Biologically Theatrical Implementations (Lies)

These are the highest-value findings. These components use biological terminology but their implementation is purely procedural, creating a false impression of biomimicry.

*   **Finding:** The "engram" is not an ensemble.
    *   **File:** `wild_igor/igor/memory/models.py` (`Memory` dataclass), `wild_igor/igor/memory/cortex.py` (`store` method).
    *   **Analysis:** A `Memory` object is stored as a single row in the `memories` table. This is a single node. Real engrams are sparse, distributed *ensembles* of co-activated neurons. The current implementation is a symbolic node in a graph, not an ensemble representation.
    *   **Verdict:** **LIE.** The central object is misnamed. A more honest name would be "MemoryNode" or "ConceptNode".

*   **Finding:** "Hebbian" co-activation is not Hebbian.
    *   **File:** `wild_igor/igor/cognition/consolidation.py` (docstring), `wild_igor/igor/cognition/hebbian_bridge.py`.
    *   **Analysis:** The docstring for `consolidation.py` claims "Hebbian co-occurrence edge strengthening" happens downstream. `hebbian_bridge.py`'s `record_retrieval_boost` function calls `word_graph.reinforce_text`, which increments a score. This is associative learning, but it's not "neurons that fire together, wire together." A true Hebbian update would modify the connection strength *between co-activated nodes* in the `memories` graph itself, based on the timing and strength of their activation. The current system boosts word weights or increments counters, which is a different mechanism.
    *   **Verdict:** **LIE.** The mechanism is associative counting, not Hebbian learning.

*   **Finding:** "Attractors" are just a sorted list.
    *   **File:** `lab/claudecode/book_learner.py` (`_score_attractor_overlap`), `wild_igor/igor/memory/cortex.py` (`get_attractors`).
    *   **Analysis:** An attractor in dynamical systems is a state or set of states toward which the system evolves over time. In TheIgors, `get_attractors` is an SQL query that does `ORDER BY activation_count * (1 + inbound_edge_count) DESC LIMIT N`. This is a ranking function, returning the top-K most popular/connected nodes. It is not a basin of attraction.
    *   **Verdict:** **LIE.** This is a Top-K query, not a dynamical systems attractor.

*   **Finding:** "Arousal" is a procedurally derived score, not a systemic state.
    *   **File:** `lab/claudecode/book_learner.py`, `_arousal_from_cp()`.
    *   **Analysis:** This function calculates an "arousal" score based on keyword hits within a narrative. Biological arousal is a global state of the nervous system, modulating neuronal excitability across the brain. While `milieu.py` attempts to model this, individual components like `book_learner` calculate their own local, procedural versions of "arousal", which is a mismatch.
    *   **Verdict:** **LIE.** This is a keyword-based relevance score, not a measure of systemic arousal.

### Honest Implementations (Positive Outliers)

These components genuinely attempt to model a biological principle, even if simplified.

*   **Finding:** The `milieu` is a plausible, simplified model of affective state.
    *   **File:** `wild_igor/igor/cognition/milieu.py`.
    *   **Analysis:** The Valence-Arousal-Dominance (VAD) model is a standard framework in computational emotion modeling. The implementation of asymmetric EMA for decay (fast rise, slow fall) and the modulation of the `basal_ganglia` threshold by arousal are legitimate biomimetic mechanisms. It's a simplified but honest attempt to model mood's effect on cognition.
    *   **Verdict:** **HONEST.**

*   **Finding:** The `inhibition_chain` and `gate_primitive` model a core neural computation.
    *   **File:** `wild_igor/igor/cognition/inhibition_chain.py`, `wild_igor/igor/cognition/gate_primitive.py`.
    *   **Analysis:** The concept of a default-inhibited action being released by a "go" signal from the basal ganglia is central to motor control and decision-making. The idea of competing signals in TWM, with gates pushing counter-signals, is a good computational analog for this inhibitory competition.
    *   **Verdict:** **HONEST.**

*   **Finding:** The `reconsolidation` module correctly models memory lability on recall.
    *   **File:** `wild_igor/igor/memory/reconsolidation.py`.
    *   **Analysis:** The docstring correctly identifies the core principle from Nader, LeDoux, et al.: recall makes a memory editable. The implementation of `mark_recalled`, `confirm_recall`, and `contradict_recall` creates a mechanism for this lability window. It's a simplified but mechanistically sound implementation of the reconsolidation principle.
    *   **Verdict:** **HONEST.**

### Missed Opportunities for Biomimicry

*   **Finding:** The core turn pipeline is overly procedural.
    *   **File:** `wild_igor/igor/main.py`, `_process_inner`.
    *   **Analysis:** The main loop is a linear sequence: thalamus -> search -> basal ganglia -> reasoner. A more biological model would be a "global workspace" (like TWM is intended to be) where multiple specialist processes (perception, memory retrieval, habit proposal) push candidates concurrently. The "winner" would be the coalition of activations that achieves the highest salience, which then becomes the focus of the next cognitive cycle.
    *   **Suggestion:** Reframe the pipeline as a salience competition in TWM. `thalamus` pushes parsed inputs, `cortex.search` pushes relevant memories, `basal_ganglia` pushes candidate habits. The `NarrativeEngine`'s job would then be to identify the winning coalition, not just to summarize.

*   **Finding:** "Sleep consolidation" is just clustering.
    *   **File:** `wild_igor/igor/cognition/consolidation.py`.
    *   **Analysis:** The current implementation clusters episodic memories by keyword and uses an LLM to extract a pattern. Biological sleep consolidation involves the replay of neural activation sequences, strengthening synaptic connections.
    *   **Suggestion:** A more biomimetic "sleep" would involve replaying the `tails` and `traces` logs, strengthening the `interpretive_edges` between co-activated nodes. This would be a true Hebbian process. The `replay.py` module seems to be intended for this but `consolidation.py` is misnamed.

## 6. Engram-Specialist Neuroscientist

My evaluation focuses on whether TheIgors' "engram" (a `PROCEDURAL` memory) aligns with empirical findings from engram research. The implementation has significant deviations from the biology.

### Findings

*   **Ensemble Encoding:** **MISMATCH.**
    *   **Analysis:** An "engram" in TheIgors is a single row in the `memories` table. Real engrams are sparse ensembles of neurons. The `payload.cells` field is a step in the right direction, suggesting a composition of smaller units, but the primary unit of storage and retrieval is the single `Memory` object.
    *   **Recommendation:** An engram should be a *collection* of memory nodes, identified by a shared `engram_id`. Retrieval would involve reactivating a subset of the ensemble, with pattern completion filling in the rest.

*   **Memory Allocation (Excitability Biasing):** **MISMATCH.**
    *   **Analysis:** Memory allocation is a deterministic `INSERT` into the `memories` table (`cortex.store`). There is no mechanism analogous to excitability-biasing, where memories are preferentially stored in neurons that are temporarily more excitable. The `arousal` field on a `Memory` object is stored *with* the memory, but doesn't influence *where* the memory is stored.
    *   **Recommendation:** A more biological allocation would involve a pool of "available" nodes, with a dynamic "excitability" score. New memories would be assigned to nodes with the highest excitability at the time of encoding.

*   **Silent Engrams:** **MISMATCH.**
    *   **Analysis:** The system does not distinguish between an engram that is encoded but not retrievable under normal conditions, and one that was never encoded. If `cortex.search()` or `cortex.get()` fails to return a node, it's treated as non-existent. There is no concept of a "silent" memory trace that could be recovered with a specific cue (the computational equivalent of an optogenetic stimulus).
    *   **Recommendation:** Introduce a `retrievability` or `strength` attribute, distinct from `activation_count`. A memory could have `strength > 0` (encoded) but `retrievability < threshold` (silent), making it invisible to normal search but potentially recoverable by a highly specific, targeted query (the "optogenetic" cue).

*   **Reconsolidation:** **MISMATCH.**
    *   **Analysis:** Memory retrieval is a read-only operation that primarily increments `activation_count`. The `reconsolidation.py` module is a positive step, creating a *window* for potential updates, but the core retrieval process itself does not destabilize and re-stabilize the memory. The content of a `Memory` node (`narrative`, `payload`) is not modified upon retrieval.
    *   **Recommendation:** On retrieval, a memory should enter a "labile" state for a short TTL. During this window, new, related information (e.g., from the current TWM) could be incorporated into the memory's `metadata` or even its `narrative` before it re-stabilizes.

*   **Systems Consolidation:** **PARTIAL MATCH.**
    *   **Analysis:** The project has a `consolidation.py` module that claims to be a "hippocampal replay analog." It clusters `EPISODIC` memories and extracts `FACTUAL` or `INTERPRETIVE` patterns. This is a plausible analog for moving specific event memories (hippocampal) to generalized knowledge (neocortical). However, the mechanism is keyword clustering and LLM summary, not neural sequence replay. The `replay.py` module seems closer to the biological mechanism but is focused on `FACT_CLOUD` nodes.
    *   **Verdict:** The *intent* matches systems consolidation, but the *mechanism* is a procedural approximation.

*   **Engram Interference & Forgetting:** **MISMATCH.**
    *   **Analysis:** There is no explicit mechanism for engram competition or interference. `cortex.search()` returns a ranked list, but the nodes themselves don't compete. Forgetting is modeled only as a decay of activation (`compute_decay_factor` in `basal_ganglia.py`), which reduces a habit's score but never deletes the memory. Memories are permanent.
    *   **Recommendation:** Introduce an "inhibition" score between similar memories. When one is retrieved, it should temporarily suppress its neighbors. Forgetting could be implemented by a garbage-collection process that archives or deletes memories whose activation count and connection strength fall below a certain threshold over a long period.

*   **Place / Context Coding:** **PARTIAL MATCH.**
    *   **Analysis:** The `memories` table has `scope`, `context_of_encoding`, and `episode` (via `episode_binder.py`) fields. This is good. However, these fields are primarily used for logging and provenance. They are not consistently used as primary keys in retrieval queries. A true context-dependent retrieval would use `WHERE context_of_encoding = 'current_context'` as a primary filter.
    *   **Verdict:** The data structures for context exist, but the retrieval mechanisms don't fully leverage them in a way that mirrors hippocampal context-dependent recall.

## 7. Cognitive Scientist

My focus is on whether Igor's architecture produces behaviors consistent with known cognitive phenomena. The vocabulary is promising, but the implementation often falls short of creating dynamic, life-like cognition.

### Findings

*   **TWM is a list, not a Working Memory:**
    *   **File:** `wild_igor/igor/memory/cortex.py` (`twm_push`, `twm_read`).
    *   **Analysis:** The `twm_observations` table acts as a temporary buffer or message queue. It lacks the core properties of a cognitive working memory:
        1.  **Limited Capacity:** TWM is capped at 50 entries, but this is an arbitrary limit, not an emergent property of competition. There's no "7±2" bottleneck.
        2.  **Competition:** While `salience` and `urgency` are used for sorting, there's no active competition where items push each other out of the workspace. It's a ranked list.
        3.  **Active Maintenance/Rehearsal:** Items in TWM simply decay via TTL. There is no rehearsal loop that keeps important items active.
    *   **Verdict:** The TWM is a database table used as a queue, not a model of Baddeley's or Cowan's working memory. This is a significant biomimetic gap.

*   **Spreading Activation is Present but Disconnected:**
    *   **File:** `wild_igor/igor/memory/cortex.py` (`spreading_activation`).
    *   **Analysis:** The system has a `spreading_activation` function, which is excellent. It traverses the word graph and interpretive edges. However, its output (a `heat_field` dict) is not consistently used to drive cognition. It's called by the `NarrativeEngine` to detect coalitions, but it doesn't seem to prime subsequent memory searches or influence the `basal_ganglia` habit selection directly.
    *   **Verdict:** The mechanism for spreading activation exists, but it's not fully integrated into the main cognitive loop. It should prime the pump for all subsequent memory operations in a turn.

*   **Priming is Absent:** There is no clear mechanism for priming. If Igor processes the word "doctor," subsequent processing of "nurse" should be faster or more likely. The current `cortex.search` is independent for each query; it doesn't carry activation state from one query to the next within a turn. Spreading activation *could* provide this, but it's not wired that way.

*   **Chunking is Misnamed:**
    *   **File:** `wild_igor/igor/tools/habit_chunker.py`.
    *   **Analysis:** This module finds sequences of `PROC_` habits in the `tails` log. This is sequence detection, a prerequisite for chunking. However, cognitive chunking is the process of binding a sequence into a single new unit that can be manipulated as one item in working memory. The `habit_chunker` creates a new `CHUNK_` memory, but it's not clear if this new chunk is treated as a single unit by the rest of the system, or if it just represents a macro.
    *   **Verdict:** This is sequence-to-macro compilation, not cognitive chunking in the Miller/Gobet sense.

*   **Attention & Fatigue:**
    *   **Attention:** The TWM gating mechanism (`TWM_CONVERSATION_ACTIVE_SEC`) is a plausible, simple model of attentional focus, suppressing background noise during active conversation. This is a positive finding.
    *   **Fatigue:** There is no model of cognitive fatigue. Igor can run indefinitely. A real cognitive system's performance degrades over time without rest. This could be modeled by having `arousal` and `dominance` in the `milieu` decay after prolonged high-activity periods, increasing the probability of errors or slower responses.

## 8. AI Safety Researcher

My focus is on predictability, alignment, and potential failure modes that could lead to unintended consequences. The system has several safety gates, but their robustness is questionable.

### Findings

*   **Tier Gating is Brittle:**
    *   **File:** `wild_igor/igor/cognition/inference_gateway.py`, `wild_igor/igor/.env` (implied).
    *   **Analysis:** The `IGOR_TIER5_ENABLED=false` and `IGOR_ARBITER_ENABLED=false` flags are simple boolean environment variables. While effective, they can be changed by any process with access to the `.env` file, including Igor's own `self_edit` tools. A sufficiently complex or erroneous self-edit could flip these flags.
    *   **Verdict:** The primary safety gates against high-cost models and autonomous action are themselves editable by the agent. This is a significant risk vector. These should be moved to a higher-level, read-only configuration layer or require a cryptographic signature to change.

*   **`scope_guard` Relies on String Matching:**
    *   **File:** `wild_igor/igor/tools/scope_guard.py`, `_TIER_TABLE`.
    *   **Analysis:** The `scope_guard` classifies file inertia based on string prefixes. This is brittle. A file rename or directory restructuring could cause a HIGH-inertia file to be misclassified as LOW, bypassing the guard. For example, if `brainstem/` were renamed to `core/`, the guard would fail.
    *   **Verdict:** The `scope_guard` is a good idea but its implementation is fragile. A more robust approach would be to store inertia levels as metadata alongside the files or in a database, rather than relying on path strings.

*   **Habit Misfire Taxonomy is Needed:**
    *   **Analysis:** The system has mechanisms to detect misfires (`response_coherence_inhibitor.py`), but there's no structured taxonomy of *why* habits misfire. This makes it hard to build systemic solutions.
    *   **Suggestion:** Classify misfires: (1) **Trigger Collision:** Multiple habits match the same trigger. (2) **Context Mismatch:** Habit fires on a keyword but the broader context is wrong (the `response_coherence_inhibitor` case). (3) **Stale Action:** The habit's `code_ref` or `response_template` is outdated. A structured log of misfires by type would be a valuable training signal.

*   **Runaway Escalation Paths:**
    *   **File:** `wild_igor/igor/tools/pe_chain.py` — The `pe_replan` loop has a 3-attempt cap, which is good.
    *   **File:** `wild_igor/igor/cognition/daemon_supervisor.py` — The watchdog that writes `restart.flag` could, in a pathological case, create a rapid restart loop if a critical thread dies immediately on startup every time. There should be an exponential backoff or a max-restarts-per-hour limit.
    *   **File:** `wild_igor/igor/tools/worker_foreman.py` — The `launch_next_worker` logic has a `_MAX_CLAIM_ATTEMPTS` guard, which is excellent. This pattern should be applied more broadly.

*   **Goal Drift:**
    *   **Analysis:** Goals are stored as `GOAL` type memories. The `goal_continuation.py` tool drives progress. Goal drift could occur if a `goal_adopt` call creates a new, conflicting goal that takes precedence, or if the `NarrativeEngine` synthesizes a new `action_impulse` that distracts from the current goal. The system relies on the salience of the `ACTIVE_GOAL` TWM entry to maintain focus, which could be fragile.
    *   **Verdict:** The goal system seems plausible but lacks hard guards against being distracted by higher-salience (but less important) TWM observations.

## 9. Systems Dynamics Analyst

My focus is on feedback loops, delays, and emergent system-level behaviors.

### Findings

*   **Runaway Positive Feedback Loops:**
    *   **TWM Salience Escalation:** A high-salience TWM observation can trigger a response, which in turn creates more TWM observations related to the same topic, further increasing its salience. Without a strong habituation or inhibition mechanism, this can lead to Igor getting "stuck" on one topic. The `boredom.py` module is the intended negative feedback to counter this, but its threshold seems high.
    *   **Self-Correction Loop:** `action_claim_verifier` and `response_coherence_inhibitor` push high-salience TWM markers when they detect a problem. The `NarrativeEngine` then processes this marker. If the NE's response *also* contains a confabulation or is incoherent, it could trigger the verifier again, creating a loop of self-correction without forward progress.

*   **Oscillations due to Delays:**
    *   **`daemon_supervisor` & `restart.flag`:** There's a delay between a thread dying, the supervisor detecting it (up to `poll_interval`), writing `restart.flag`, the main loop detecting the flag, and the system restarting. During this window, Igor could be operating in a degraded state. If the restart is slow, the system could oscillate between running and restarting.
    *   **`env_sync`:** `HeartbeatSource` checks for `.env` changes every 5 minutes. If a change is made, it might not take effect for up to 5 minutes, leading to behavior based on stale configuration.

*   **Unintended Couplings:**
    *   **`milieu` and `basal_ganglia`:** Arousal modulates the habit-firing threshold. This is an intended coupling. An *unintended* effect could be that a stressful event (e.g., a series of tool failures) raises arousal, which raises the habit threshold, making it *harder* for corrective habits to fire, potentially worsening the situation.
    *   **`cortex.search` and `word_graph`:** The `hebbian_bridge.py` creates a feedback loop. `word_graph` predictions boost search candidates. Successful retrieval reinforces the `word_graph`. This is a classic "rich get richer" loop. It can lead to the system over-specializing and becoming unable to retrieve novel but relevant information that doesn't align with the word graph's current state.

*   **Missing Feedback Loops:**
    *   **Tool Latency → Tier Selection:** The `inference_gateway` doesn't seem to have a feedback loop from observed tool latency back to its routing decisions. If a particular tool becomes consistently slow, the gateway should learn to de-prioritize reasoning paths that rely on it.
    *   **Cost → Habit Compilation:** The system logs the cost of cloud calls, but there's no direct feedback loop that says "this query cost $0.05; prioritize compiling a habit for it." The `self_trainer.py` is close, but it's based on gaps, not explicitly on cost.

## 10. QA Skeptic / Test Engineer

My job is to break things. I look for untested paths, fragile assumptions, and failure modes nobody has considered.

### Findings

*   **Critical Paths with Low/No Coverage:**
    *   **Error Handling:** The numerous `except Exception: pass` blocks are, by definition, untested code paths. We have no idea what happens when these exceptions are actually thrown.
    *   **`db_proxy.py` SQL Translation:** The SQLite-to-Postgres translation layer is critical and complex. There are no specific tests for `_translate_insert_or_replace` or the `?` to `%s` logic. A subtle bug here could cause data corruption.
    *   **Concurrency:** There are almost no tests for concurrent operations. What happens if two threads try to `store_memory` at the same time? What if `cc_queue.py` is accessed by multiple processes? The `ThreadedConnectionPool` helps, but application-level race conditions are likely.

*   **Tests Passing by Accident:**
    *   Many tests rely on `time.sleep()` to wait for background threads. This is a recipe for flaky tests. A test might pass on a fast machine but fail on a slow one. Proper synchronization (Events, Queues, Conditions) should be used.
    *   Fixtures that create a pristine database for every test might mask bugs that only appear with a large, complex memory graph (e.g., performance issues in `cortex.search`). We need a set of tests that run against a pre-populated, realistic "aged" database.

*   **Fragile Assumptions & Unstated State:**
    *   **Filesystem State:** Many tools and modules assume the existence and state of files in `~/.TheIgors/` (e.g., `cc_queue.json`, `milieu.json`, `machines.json`). Tests should explicitly set up and tear down this state, not rely on the developer's local environment.
    *   **Environment Variables:** The code is heavily dependent on environment variables. Tests should use `unittest.mock.patch.dict` to control the environment for each test case, ensuring reproducibility.
    *   **`sys.path` Manipulation:** The `sys.path.insert` calls in `book_learner.py` and `igor_base.py` are a huge red flag. This makes test discovery and execution dependent on the current working directory and can lead to importing the wrong version of a module.

*   **Self-Testing & In-Process Monitoring:**
    *   The `daemon_supervisor` is a good start, but Igor could be more proactive.
    *   **Invariant Checks:** Igor could periodically run checks like `verify_genesis_integrity()` or `cortex.integrity_check()` as a background habit. If a check fails, it could raise a high-urgency TWM alert.
    *   **Behavioral Regression:** After a self-edit, Igor could run a small, targeted set of "smoke test" queries against himself to verify that core capabilities (like answering "what time is it?") are still functional. This is a faster feedback loop than waiting for the full `pytest` suite.

## 12. What Else?

### What else should we be asking?

*   **What is the "unit of thought"?** Is it a turn? A `pe_chain` run? A `NarrativeEngine` cycle? The codebase doesn't have a clear, consistent answer. Defining this would clarify the architecture. A "thought" should probably be a transactionally coherent update to the memory graph.
*   **What is the model for time?** The system uses `datetime`, `time.monotonic`, and `time.time` inconsistently. There's no unified `Clock` service. This will lead to subtle bugs related to timezones, sleep/wake cycles, and event ordering.
*   **Where does "self" live?** Identity is scattered across `IDENTITY.md`, `SOUL.md`, `ID*` memories, and the `igor_identity_master.dsb`. A single, canonical `Self` object or facia node would provide a clearer anchor for introspection.

### How can we help him learn and reason better?

*   **Embrace the Biomimicry:** The most promising parts of the architecture are the most biological (`milieu`, `reconsolidation`, `inhibition_chain`). Double down on these. Replace procedural logic with competitive, emergent dynamics wherever possible. The "attractor" implementation is the most urgent target for this refactor.
*   **Strengthen the Feedback Loops:** Learning happens in loops. The `self_trainer.py` and `output_trainer.py` are good examples. We need more of them. Every action Igor takes should have an observable outcome, and that outcome should feed back into the system to adjust future behavior. The `reconsolidation.py` module is key here; it needs to be wired into more downstream consumers.
*   **From Chains to Networks:** The `pe_chain.py` is a linear process. Real reasoning is not. Refactor it into a network of engrams using the `cursor_runtime.py`. Let the path be determined by the state of the basket, not a hardcoded sequence of function calls.

### How can we optimize for small hardware?

*   **Aggressive Caching:** The system already has several caches (`reasoning_cache`, `_mem_cache`). These need to be more aggressive and have clear eviction policies (LRU, LFU).
*   **Reduce Database Chattiness:** The N+1 problems identified by the DBA are major performance killers. Batching writes and using JOINs for reads will dramatically reduce DB load. Using `LISTEN/NOTIFY` instead of polling will reduce idle CPU usage.
*   **Offload to `pg_cron`:** Any periodic task that can be expressed in SQL (e.g., cleaning up old TWM entries, calculating summary stats) should be moved to `pg_cron` to run inside the database, freeing up application process resources.
*   **Model Quantization:** The reliance on `qwen2.5:7b` is good. Explore even smaller, quantized models for tasks like preparse or simple classification. A 1-3B parameter model could handle many of the tasks currently assigned to the 7B model, freeing up VRAM.

### How do we perform the same review process of the database and its engrams?

This is a critical question. The code is only half the system.
1.  **Engram Audit Skill:** Create a new `/audit-engrams` skill.
2.  **Input:** The skill would query the database for all `PROCEDURAL` and `INTERPRETIVE` memories.
3.  **Personas:** It would then use a multi-persona LLM call (similar to `/deep-audit`) to review the *engrams themselves*.
    *   **Logic Persona:** Does the `payload.cells` logic make sense? Are there dead ends or infinite loops in the `BRANCHIF` graph?
    *   **Linguist Persona:** Is the `narrative` clear? Does the `trigger` accurately reflect the narrative's intent?
    *   **Biomimicry Persona:** Does this engram represent a plausible cognitive function, or is it just a procedural script in a fancy format?
    *   **QA Persona:** What inputs would make this engram misfire?
4.  **Output:** A report of suspect engrams, with recommendations for `DELETE`, `MERGE`, or `REFACTOR`. This process makes the graph itself subject to the same critical review as the code.
