PROBLEM|
  tails table in live DB is missing trail_id and sequence_pos columns.
  Migration was wrapped in a bare `except` and silently failed.
  Result: whole trail subsystem has been running on empty data since columns were added.
  Also: no trail_metadata table exists — trails are not first-class objects.

PHANTOM_DATA_FIX|
  Named migration: "tails_v2_trail_id_sequence_pos"
  ALTER TABLE tails ADD COLUMN IF NOT EXISTS trail_id TEXT;
  ALTER TABLE tails ADD COLUMN IF NOT EXISTS sequence_pos INTEGER;
  CREATE INDEX IF NOT EXISTS idx_tails_trail ON tails(trail_id);
  CREATE INDEX IF NOT EXISTS idx_tails_node ON tails(node_id);
  CREATE INDEX IF NOT EXISTS idx_tails_time ON tails(recorded_at);
  Gate: store migration name in cortex._migrations; skip if already applied.

DESIGN|
  Trails are first-class objects. A trail = one search traversal.
  tails = heat/Hebbian signal (decay per node, training signal)
  trail_activations = provenance (which nodes fired, in what order, for this trail)
  These are two different views of the same underlying activation event.
  Trails persist permanently. Tails decay (heat fades, trail record stays).

NEW_TABLE|trail_metadata|
  id TEXT PRIMARY KEY,           -- UUID, minted by cortex at search start
  started_at TIMESTAMP NOT NULL,
  closed_at TIMESTAMP,           -- set by cortex when traversal returns (cortex owns lifecycle)
  query_text TEXT,               -- the search query that spawned this trail
  purpose TEXT,                  -- 'search' | 'habit_trigger' | 'ne_consolidation' | 'interoception'
  twm_obs_id TEXT,               -- nullable soft FK to twm_observations.id
                                 -- makes trail = trace of a TWM attractor's propagation
  instance_id TEXT,
  thread_id TEXT

NEW_TABLE|trail_activations|
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  trail_id TEXT NOT NULL,        -- FK to trail_metadata.id
  node_id TEXT NOT NULL,         -- FK to memories.id
  sequence_pos INTEGER NOT NULL, -- traversal order within this trail
  activation_weight REAL,        -- how strongly this node fired
  activated_at TIMESTAMP NOT NULL

TWM_TRAIL_JOIN|
  trail_metadata.twm_obs_id is a nullable soft FK.
  When a TWM attractor drives a search (NE, BG habit scoring, cortex.search from active slot):
    - mint trail at search start
    - set twm_obs_id = active attractor's obs_id
  This makes the trail = the trace of that attractor's influence propagating through the graph.
  Useful later: which TWM attractors produce the richest traversal paths?

TAILS_VS_TRAIL_ACTIVATIONS|
  tails: heat per node, decays, used for Hebbian co-activation training
    Purpose: "how hot is this node right now?"
  trail_activations: provenance per traversal step, permanent
    Purpose: "what path did this search take?"
  Both get written at search time. They serve different things even though they're
  different views into the same activation event.

THREE_TEMPORAL_SYSTEMS|
  milieu: body baseline, alpha=0.05 (slow drift, like body temperature)
  TWM: attractor decay per slot (urgency-weighted, fast for emergency obs)
  tails: per-node heat decay (Hebbian gradient signal)
  trail_metadata links them: a trail has a TWM attractor origin, leaves tails heat,
  and its timing lives in milieu-adjusted context.
